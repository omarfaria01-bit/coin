### 1.2 jup-ag/distributor — leaf format (enough to implement `engine/merkle.py`)

Source (master, as fetched 2026-11-14):

- Program ID: `declare_id!("DiS3nNjFVMieMgmiQFm6wgJL7nevk4NrhXKLbtEH1Z2R")` in [`programs/merkle-distributor/src/lib.rs`](https://github.com/jup-ag/distributor/blob/master/programs/merkle-distributor/src/lib.rs)
- Verification in [`programs/merkle-distributor/src/instructions/claim/new_claim.rs`](https://github.com/jup-ag/distributor/blob/master/programs/merkle-distributor/src/instructions/claim/new_claim.rs)
- Off-chain node preimage in [`merkle-tree/src/tree_node.rs`](https://github.com/jup-ag/distributor/blob/master/merkle-tree/src/tree_node.rs)
- Tree construction in [`merkle-tree/src/merkle_tree.rs`](https://github.com/jup-ag/distributor/blob/master/merkle-tree/src/merkle_tree.rs)

Hash function is Solana `hashv`, i.e. **SHA-256**, not keccak.

Field order and types for the inner node:

1. `claimant`: `Pubkey` (32 bytes, raw)
2. `amount_unlocked`: `u64` **little-endian** (called `amount` in `TreeNode`)
3. `amount_locked`: `u64` **little-endian** (`locked_amount` in `TreeNode`)

There is **no index** in the leaf.

Second-preimage defense (domain-separated prefixes):

```
LEAF_PREFIX          = 0x00
INTERMEDIATE_PREFIX  = 0x01

inner = sha256(claimant[32] || amount_unlocked_le[8] || amount_locked_le[8])
leaf  = sha256(0x00 || inner)                         # 33-byte preimage
parent = sha256(0x01 || left[32] || right[32])        # 65-byte preimage
```

`TreeNode.hash()` returns only `inner`. The Merkle tree wrapper applies `LEAF_PREFIX` when inserting leaves. `engine/merkle.py` must do the same or proofs will not verify.

Claim instruction: `new_claim(amount_unlocked: u64, amount_locked: u64, proof: Vec<[u8; 32]>)`. Claimant is the signer. A `ClaimStatus` PDA is created at seeds `["ClaimStatus", claimant, distributor]` — one claim record per (claimant, distributor), not per epoch version inside the same account.

**New tree / re-funding each epoch:** the distributor PDA is

```
["MerkleDistributor", base, mint, version_u64_le]
```

`new_distributor` **inits** that account and writes `root` once. There is no "update root" instruction in the admin module. A new epoch needs a **new `version`** (new PDA), a new root, and a freshly funded token vault (the vault is the distributor's ATA). You cannot reuse the same distributor account to publish a new tree. After `end_vesting_ts`, `clawback_start_ts` must be at least **one day** later; then admin can claw back unclaimed tokens.

For a plain epoch payout with no vesting inside the distributor, set `amount_locked = 0` and still include those 8 zero bytes in the leaf. Vesting timestamps are still required by `validate()` (`start_vesting_ts < end_vesting_ts`, both in the future, clawback ≥ end + 1 day).

**Claim flow:** admin creates distributor + funds vault → claimant submits proof → unlocked amount (plus any bonus defined on the distributor) is transferred from the vault; locked amount vests between `start_ts` and `end_ts` and is claimed later via `claim_locked`. Closable flag is documented in source as testing-oriented.

**Rent/costs:** README (inherited from the Saber/Uniswap writeup) claims claimer-paid rent on the order of `0.000010 SOL` historically. Treat current rent as **UNVERIFIED** — measure on devnet before launch. Claimers pay their own tx fee.

**Token program:** `NewClaim` and `NewDistributor` declare `token_program: Program<Token>` (legacy SPL Token). Do not assume Token-2022 mints work. If the pad issues Token-2022, this is a blocker until proven otherwise.

### 1.4 Saber template and Solana Foundation example

**Saber** (`declare_id` and claim in [`programs/merkle-distributor/src/lib.rs`](https://github.com/saber-hq/merkle-distributor/blob/master/programs/merkle-distributor/src/lib.rs)):

```
leaf = keccak256(index_u64_le || claimant_pubkey[32] || amount_u64_le)
```

No `LEAF_PREFIX`. Proof verification uses the program's `merkle_proof::verify`. The claim `index` is part of both the leaf and the `ClaimStatus` PDA. Last meaningful commit is 2022. Do not pick this as the primary rail unless everything else is blocked — it is stale.

**Solana Foundation example** ([README](https://github.com/solana-foundation/program-examples/blob/main/tokens/merkle-tree-token-claimer/README.md)):

- Leaf **bytes** are exactly 40 bytes: `solana_pubkey[32] || amount_u64_le[8]`.
- `leaf_hash = sha256(leaf_bytes)`.
- Parent: `sha256(left || right)`.
- Odd levels padded with a **32-byte zero hash** (not a duplicated node). README explains why duplication would allow one proof under two indices.
- This is a template to deploy yourself. COIN_MATH §13 says not to write/deploy a custom distributor if an existing audited one works. Use this only as a reference for tests or as a last resort.

### 1.5 Recommendation (Claude decides)

**Recommend jup-ag/distributor** as the default claim rail for classic SPL Token payouts:

- Leaf and tree are fully specified from source, so `engine/merkle.py` can be written without guesswork.
- Same program ID on mainnet and devnet (verified).
- New `version` per epoch matches our `epochs/<n>/root.txt` flow; unclaimed funds can be clawed back after the delay.
- Caveats to accept in DECISIONS.md: GPL-3.0 (do not vendor source without legal #8), no audit PDF found, code last default-branch commit Feb 2025, **legacy SPL Token only**, program is upgradeable (upgrade authority `CvQZZ23qYDWF2RUpxYJ8y9K4skmuvYEEjH7fK58jtipQ` on mainnet as of this check).

**Do not pick Saber** (stale). **Do not deploy the Foundation example** unless no hosted program can pay our mint type. **Revisit Streamflow** if (a) the mint is Token-2022, or (b) Streamflow publishes the leaf format — their SDK and audit are otherwise stronger on maintenance.

Off-chain Python should implement the chosen leaf itself (`hashlib` SHA-256 or `solders`/`keccak` as required) plus tests against independently computed vectors. Already in `pyproject.toml`: `numpy`, `hypothesis`, `pytest`. No new on-chain crate required for the engine.

### 2.2 Request → reveal (how this maps to COIN_MATH §9)

COIN_MATH: publish the snapshot hash, **then** request VRF, derive `u_c = uniform(0,1)` from `hash(randomness || cluster_id)`, then Efraimidis–Spirakis. Engine already specifies SHA-256 of `randomness || cluster_id` in `engine/draws.py`.

**ORAO Classic (fits this):**

1. Publish `epochs/<n>/inputs.json` (includes data hash).
2. Submit `Request` / `RequestV2` with a 32-byte seed derived from that hash (do not use a seed anyone could have requested earlier).
3. Wait for fulfillment; read 32 bytes from the randomness PDA (`randomness_account_address(seed)`).
4. Feed those bytes into `draw_winners` off-chain. No callback program required for v1.

**Switchboard On-Demand:**

1. Create / commit a randomness account tied to a slot/slothash **after** the snapshot is published.
2. Oracle writes the value.
3. Reveal and read `get_value`. Do not let a caller abort after seeing the value.

### 2.3 Recommendation

**Recommend ORAO Classic VRF** for v1 draws:

- Official IDs are identical on devnet and mainnet (verified), which simplifies P5.
- Apache-2.0, repo touched 2026-11-02, Rust/TS SDKs current (`0.8.1`).
- Published fee 0.001 SOL (re-check NetworkState at integration).
- Off-chain consume matches our engine (we do not need a callback program yet).
- Use the snapshot hash as the request seed so the commit/reveal order in §9 is auditable.

Keep Switchboard On-Demand as the documented alternative if we later want TEE-attested oracle randomness or are already on Switchboard feeds. Price must be read from the live queue before that decision. Do not write a custom VRF.

## 4. Token-2022 transfer hooks

### 4.1 Status

Token-2022 transfer hooks run a user-specified program on every transfer, including pool vault moves. Official integration guide: [solana.com/docs/tokens/extensions/transfer-hook-integration](https://solana.com/docs/tokens/extensions/transfer-hook-integration). For native vesting (COIN_MATH §11 mode A) a hook would enforce `balance − locked ≥ 0`. That only works if every venue we trade on will still transfer the mint **with the hook still attached** after launch.

### 4.2 Venue matrix (2026-11-14)

| Venue | Official source | Token-2022 generally | Transfer hooks |
| --- | --- | --- | --- |
| Raydium CPMM / CLMM | [Token-2022 support matrix](https://docs.raydium.io/reference/token-2022-support) | Yes, but only an extension allow-list: TransferFeeConfig, MetadataPointer, TokenMetadata, InterestBearingConfig, ScaledUiAmount. AMM v4 / Stable AMM: no Token-2022 | **Rejected at pool creation.** Docs name TransferHook explicitly as unsafe (arbitrary CU, reentrancy). Only bypass is an admin per-mint registry PDA. ### 4.3 Recommendation

**Do not rely on Token-2022 transfer hooks for v1 vesting.** After launch, the venues that matter (Raydium CPMM/CLMM, Meteora post-graduation, Jupiter Trigger) reject or strip hooks. Default `config/pad.json` `vesting_mode` to **`soft`** unless a specific pad documents a hook that (1) survives graduation and (2) is accepted by the post-graduation AMM **and** by Jupiter routing. That would be an exceptional, sourced finding at pad-watch time.

Soft-mode limits (COIN_MATH already states them) must stay in `PUBLIC_RULES.md`: early buyers can still dump; we only claw rewards.
